# v3.0.0-rc.5 — Faster phone upload, staged server ingest

This release has two halves that can be installed separately: a new phone build
and a new server (schema 3). The telemetry wire contract is unchanged, so either
half works with the other and with rc.4.

## Phone

- **Uploads keep up with a backlog.** The phone sends as soon as records are
  saved, with up to 8 messages in flight, and reads enough per round to fill
  them. Target for a real LAN run: at least 1,500 records/s, and a 10-minute
  backlog cleared in under 3 minutes. These targets are not yet measured.
- **A full storage budget no longer stalls recording.** Records that cannot be
  stored are counted once as a Recording_Loss event, and recording resumes when
  the backlog drains. Lap markers, recovery events and session metadata are
  always kept. Conflicting records go to a new FAILED RECORDS count in storage
  health.
- **Removed:** the Config -> Throttle mapping screen (the app no longer sends
  CMD:THROTTLE_MAP) and the in-app driver alerts (audio, haptic, thresholds).
  The ESP32 firmware must use a fixed default throttle curve; this is pending
  confirmation from the firmware owner. Grafana alerts are unchanged.

Install the signed APK over rc.4, then fully close and reopen the app. Do not
uninstall or clear app data. The phone journal upgrades itself from schema 4 to
5 and keeps pending records. It cannot be downgraded: going back to rc.4 needs
a journal reset.

## Server (schema 3, clean cutover)

- Telegraf now writes plain staging tables, and a TimescaleDB job merges them
  into the typed tables every second in one set-based pass. Latest signal values
  and session bounds are kept up to date by that job, so Grafana alerts and
  session discovery no longer scan telemetry history.
- Lap and power averages are weighted by the time each second was covered.
  Alerts watch a new session from its first samples, before its metadata
  arrives.
- Mosquitto queues are bounded by bytes: 1.5 GB per client, about two hours of
  phone traffic while SQL is down. Lower `max_queued_bytes` in
  `ops/backend/mosquitto.conf` if the host has little memory. The queues are
  held in RAM. Autosave runs every 30 s. In the Compose layout the broker can
  now save to its volume, so queued messages survive a broker restart.
- The server CSV logger acknowledges a message only after its rows are written
  to disk.

**An existing server database is not migrated.** The stack reports it unhealthy
and leaves the volume untouched. Follow "Schema 3 server cutover" in
[cutover.md](../implementation/cutover.md): keep the Mosquitto volume, start
with a new database volume, and replay any missing rows from phone journals or
server CSV.

## Verification

- `flutter analyze` is clean and `flutter test` passes (104 tests, 1 skipped).
- `tools/qualify_backend.py` passes for both the Compose and single-container
  layouts, including outages, a 3,200-record burst, and resending old rows
  mixed with new ones into compressed data. Publish-to-SQL latency was about
  0.8-2.6 s.
- **Not tested:** the phone on a real LAN at the speed targets above, and the
  Android/CAN hardware path. See
  [verification.md](../implementation/verification.md). Treat this as a release
  candidate until those pass.
