# v3.0.0-rc.6 — Ingest recovers at once after a database restart

This is a server fix. The phone build is the same as rc.5 apart from the version
number, and the telemetry wire contract is unchanged.

## The bug in rc.5

If the database restarted, stopped or crashed while the ingest job was in the
middle of a batch, TimescaleDB held that job back for about 5 minutes, and SQL
ingest stopped for that time. Nothing was lost: rows stayed staged or queued and
were ingested afterwards. Dashboards and alerts lagged for those minutes.

## The fix

Two identical ingest jobs now share the ingest lock. Only the one holding the
lock can be caught mid-batch; the other takes over at once and replaces the held
job with a fresh one. In testing, ingest resumed 2-4 s after a restart that
landed mid-batch. A restart that catches both jobs mid-run at the same moment
can still wait the 5 minutes; this is rare.

## Upgrading

**The schema fingerprint changed, so a database created by rc.5 is refused.** It
is reported unhealthy and left untouched. Follow "Schema 3 server cutover" in
[cutover.md](../implementation/cutover.md): keep the Mosquitto volume, start a
new database volume, and replay any missing rows. A server still on rc.3 or rc.4
needs the same steps. The phone needs no reset: install the APK over rc.4 or
rc.5, then close and reopen the app.

Everything else in [rc.5](v3.0.0-rc.5.md) applies unchanged, including the
untested hardware path (phone-on-LAN speed targets and Android/CAN).

## Verification

CI on `main` passed, including both backend layouts. The new restart-recovery
check kills the database mid-batch and requires ingest within 60 s; rc.5 fails it
every time.
